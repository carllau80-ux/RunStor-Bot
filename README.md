# RunStor Bot

把自然语言描述的备份或恢复需求，解析成结构化的计划 JSON；对服务器做 SSH 自动化巡检并把
结论写成 PDF 报告；内置一个轻量知识库（导入 Markdown 手册，提问给出带引用的回答，巡检
结论自动引用相关章节）。信息不完整时逐项追问，补齐后输出完整 JSON。

Go 实现，产物是**单个静态二进制**（`CGO_ENABLED=0`，无运行时依赖、无需 Node/Python/数据库），
内置网页界面，界面支持**中文/英文**与**深色/浅色主题**。构建期有少量依赖（TOML 解析、纯 Go SQLite
等，见 `go.mod`），`go.sum` 已入库。

```
用户: 周天全备份oracle数据库，每天增量备份，oracle使用系统认证，备份整个实例，并发设置为4

Agent: [已识别] 引擎=oracle  认证=系统认证  范围=整实例  并发=4
               全备=每周日    增量=每天
       [待补充 4 项]
         1. 全量备份在几点执行?            (schedule.full.time)
         2. 增量备份在几点执行?            (schedule.incremental.time)
         3. 备份保留多久?                  (retention)
         4. 备份存储到哪里?                (destinations)

用户: 都是凌晨1点，保留14天，存在本地 /u01/backup/orcl

Agent: [完成] status=ready  →  输出完整计划 JSON
```

## 快速开始

```bash
make build
./bin/backup-restore-agent --check      # 只做配置自检
./bin/backup-restore-agent              # 启动, 打开 http://127.0.0.1:8081/
```

**无需任何 API Key**：没有可用模型配置时自动进入 demo 模式，使用内置的关键词规则
客户端跑通全流程。适合离线演示、接口联调与冒烟测试。配置模型后自动切换。

## 三条核心设计

### 1. 通用 schema + 引擎驱动注册表

Oracle 只是举例。引擎差异不写进 schema 主体，而是由驱动声明：

```
internal/driver/oracle.go   一个文件定义 Oracle 的完整支持
  ├─ 槽位表     ──┬─> options 的 JSON Schema (喂给模型)
  │               ├─> 缺什么就问什么 (缺口分析)
  │               └─> 取值校验 (报错带精确路径)
  ├─ 别名       ──> 从中文里认出引擎
  └─ 术语映射   ──> "整实例" -> whole_instance
```

槽位表是单一事实源。**新增一个引擎不需要改提示词、缺口分析、接口或测试**——
提示词里的 options schema 是从槽位表生成的。

已内置：`oracle`、`mysql`、`postgresql`、`file`，以及兜底的 `other`（未注册引擎也
不中断流程，只是不校验其专属参数）。

### 2. 完整性由确定性槽位表判定，不由模型判定

模型只负责"把中文读懂并填 JSON"；"JSON 是否完整"由槽位表判定。这带来两个性质：

- **能终止**：待问问题来自有限的确定性检查，每填一个槽位就少一个问题；
  另有轮次上限（默认 10 轮）作为最终熔断，绝不会无限追问。
- **不重复**：答案按稳定的槽位路径（如 `source.items[0].options.auth_mode`）回传，
  不依赖问题原文匹配。问题文案可以随便改，答案的归属始终不变。

模型不能自己提问题（提示词明确禁止），它生成的 `warnings` 只作为风险提示。

### 3. 两条回填路径并存

用户对追问的回答会同时走两条路：

- **确定性路径**：`"凌晨1点"` → `01:00`、`"系统认证"` → `os_auth`、`"保留14天"` → `{value:14,unit:days}`。
  可解析的一定落盘，且**用户明确回答的值优先于模型的理解**。
- **模型路径**：规则解析不了的说法（"大概两周吧"）原样进入下一轮提示词，由模型理解。

```json
  "plan": { ... },
```

### 恢复计划

恢复意图产出独立的 `RestorePlan`，字段与备份计划不同：
`source_backup_ref`（从哪份备份恢复）、`target`（原机/异机、主机、实例）、
`point`（`latest`/`timestamp`/`scn`/`lsn`/`backup_set_id`）、`scope`（全库/库/表空间/表/文件）、
`alternate`（换目录/换实例名/仅校验）、`verification`。

## 服务器自动巡检

在网页顶部切到 **巡检**：填服务器地址、登录用户、密码（或私钥），即可通过 SSH 连上去检查
**CPU、内存、磁盘分区、温度、严重错误日志**，外加失败的服务单元。多台机器用逗号或换行分隔
（单次上限 50 台），并发数可配。

每项检查给出结论（正常 / 告警 / 严重 / 无法判定）与原始证据，整份报告落盘留存，可回看、可删除，
并可**导出成 PDF**（报告卡片上的「导出 PDF」，或走接口 `GET /api/inspect/{id}/report.pdf`）。

```
控制台 → [巡检] → 10.0.0.1,10.0.0.2
        用户 root  密码 ****
   ● CPU 负载    ok       1 分钟负载 0.40, 每核 0.05（8 核）
   ● 内存        ok       已用 41.2%, 可用 4.5 GB / 7.8 GB
   ● 磁盘分区    critical /data 使用率 95%, 已接近写满
   ● 温度        warn     Package id 0 达 84.0°C, 偏高
   ● 严重错误日志  critical 发现 2 条严重日志（内核 panic/OOM/硬件错误等）
   ● 服务状态    ok       没有失败的服务单元
```

### 安全约束

| 项 | 做法 |
|---|---|
| 密码与私钥 | **只在内存里用于本次连接**，不写日志、不落盘、不回显 |
| 密码传递 | 经环境变量交给 ssh 子进程，**不进 argv**（`ps` 对同机用户可见） |
| 凭据隔离 | ssh 只用本次提供的凭据（`IdentitiesOnly=yes` + `IdentityAgent=none`），**不会回退去用 ssh-agent 里的密钥** |
| 认证方式 | 按凭据裁剪：只给私钥就只试 `publickey`，只给密码就只试密码类认证 |
| 远端脚本 | **固定文本**，用户输入（主机/用户/密码）只作为 ssh 的参数，绝不拼进脚本 |
| 私钥临时文件 | 0600，用完立即删除 |
| 主机指纹 | 默认 **TOFU**：已知主机按 `known_hosts` 严格校验，未知主机接受但**把指纹写进报告**并提示 |
| 执行时限 | 一次连接有总预算（连接超时 + 各项检查超时之和 + 余量），到点连同子进程一起终止 |
| 巡检记录 | 报告落盘（0600），**不含任何凭据** |

**"凭据隔离"这条为什么必须有**：ssh 默认会在给出的密钥被拒后回退去用 ssh-agent 里的密钥，
于是一个**错的私钥或错的密码也可能连上**，用户会以为自己的凭据是有效的 —— 而巡检的结论
正是"用你给的凭据能不能连上"。同理，认证方式里绝不列上本次没有给出凭据的那一类，
免得白试一次在目标机上留下失败计数（有的环境配了 fail2ban 或账号锁定）。

**"执行时限"这条也一样**：远端脚本里每项检查都自带 `timeout`，但那要登录成功才生效；
目标机接受 TCP 连接却在认证后失去响应时，ssh 自己会一直等下去，一次巡检就能把请求永久挂住。
所以有总预算，到点连 ssh 及其派生进程一起收掉，报告里注明"已终止 + 可能的原因"。

`host_key_policy` 可选 `tofu`（默认）/ `strict` / `insecure`。要严格校验就先自己把目标机指纹
写进 `known_hosts`，再把策略设为 `strict`。

> 注意：巡检让这个服务具备了"用任意凭据连接任意主机"的能力，而当前**没有鉴权**。
> 请只在受控内网暴露该端口；不需要该功能时设 `inspect.enabled=false` 关掉。

### PDF 报告

PDF 是**服务端按需生成**的（同一份记录永远是同一份内容）：A4 版面，结论条按严重程度着色，
逐项检查带原始证据，页脚有页码与生成时间。文字**可以复制、可以搜索** —— 运维常要把日志片段
粘到工单里，一份只能看不能选的文件是半个工具。

要点：

| 项 | 做法 |
|---|---|
| 实现 | 手写 PDF 生成（`internal/pdfdoc`），不引第三方库 —— 与项目其他部分一致：构建环境不通外网 |
| 中文字体 | **内嵌**在二进制里。PDF 内置的 14 种标准字体一个汉字都没有，不嵌字体就只能显示空白 |
| 两份字体 | 拉丁/符号用 DejaVuSans，中日韩用 DroidSansFallback，按字符选择、行内混排（详见 `internal/pdfdoc/assets/NOTICE.md`，含许可与来源） |
| 子集化 | 只嵌入报告里真正用到的字形（几十 KB），不是把整份字体塞进去 |
| 换行 | 中文逐字断行、西文按词断行，并处理行首/行尾禁则（收尾标点不出现在行首） |
| 可复制 | 生成 ToUnicode 映射，所以复制出来的就是原本的中文，而不是字形编号 |
| 缺字形 | 字体确实画不出的字符替换成 `□`，并在报告末尾列出对应的码位 —— 不静默丢字 |
| 自定义字体 | `inspect.pdf_font` 可指定别的 TrueType 字体替换拉丁部分（CFF/OpenType 轮廓的字体不支持，启动时会提示并退回内置字体） |

### 判定阈值

集中在 `internal/inspect` 的 `Thresholds` 里（便于日后做成可配置）：负载每核 >1 告警 / >2 严重；
可用内存 <20% 告警 / <10% 严重；磁盘 ≥80% 告警 / ≥90% 严重；温度 ≥80°C 告警 / ≥90°C 严重；
出现内核 panic/OOM/硬件错误即严重；有失败的服务单元告警。

两条刻意的"诚实性"设计：**读不到温度**（虚拟机常见）与**读不到日志**（容器里 `dmesg` 常被限制）
都报"无法判定"而不是"正常"——否则会给出虚假的安心。

### 实现取舍：为什么用系统 ssh 客户端

Go 的 `golang.org/x/crypto/ssh` 是更"正统"的做法，本项目也一度因为它而改用了系统 ssh：那时
构建机取不到模块（`x/sys`、`x/term`），而项目要能离线从零构建。引入依赖之后这个前提不成立了，
但**保留系统 ssh 客户端**仍然是对的，理由换成了三条更实际的：

- 它与运维手工排障时用的是**同一个客户端**，`known_hosts`、`ProxyJump`、`~/.ssh/config` 的行为一致，
  不会出现"命令行能连、系统连不上"；
- TOFU 语义（`accept-new`）与主机指纹由 OpenSSH 自己实现，不必自己维护一份信任库逻辑；
- 凭据交给 ssh 处理，本项目不持有任何密码学实现（问密码走 `SSH_ASKPASS` + 环境变量，不进 `argv`）。

代价是目标机需装有 ssh 客户端（Linux 服务器默认都有，`deploy/install.sh` 会预检）。

## 知识库（RAG）

把运维手册、故障处置流程这类 Markdown 文档导入进来，之后：

- **提问**：切到「知识库」标签，输入问题，得到**只依据这些文档**的回答，并标注引用编号；
  点开引用能看到是哪份文档的哪一节、原文是什么。
- **巡检报告自动引用**：巡检发现的问题（日志影响分析那部分）会自动附上手册里相关章节，
  报告里显示成 `相关知识: 《iSCSI 存储链路故障处置》§ 登录被拒绝 / 安全协商失败`。
  PDF 导出里也有。

### 检索是怎么做的

**词法检索（BM25），不是向量检索**，这是刻意的取舍：

| 原因 | 说明 |
|---|---|
| 端点兼容 | 很多 OpenAI 兼容端点没有 `/embeddings`（预设里的 DeepSeek 就没有），向量检索在那些环境下直接不可用 |
| 无需外部依赖 | 不引向量库、不引分词器、不引模型，离线可用，检索结果可复现、可解释（哪几个词命中、为什么这条排前面都能说清） |
| 中文没有分词器怎么办 | 用**字符二元组**索引：`存储池降级` → `存储/储池/池降/降级`。这是检索领域对中文的经典退化方案，不需要词典 |
| 术语优势 | 运维文档里最有区分度的词（`zpool`、`scrub`、`OOM`、`iSCSI`、`CHAP`、`checksum`）都是低频专有词，正是 BM25 最擅长区分的类型 |

实测（.38 的真实日志 + 真实手册）：`zpool 校验失败怎么办` 命中 `《ZFS 手册》§ 校验失败`（相关度 8.1），
`iSCSI 登录被拒绝` 命中 `《iSCSI 手册》§ 登录被拒绝 / 安全协商失败`（相关度 11.3）。

**检索词扩展**：提问时可以让模型把问题改写成若干检索词（默认开启），用来补"同义不同词"的缺口 ——
例如用户问"磁盘写满了"，手册写的是"空间不足"，字面二元组对不上。扩展词只做**补充召回**，
权重是原问题的 0.4 倍，不会盖过用户原话的命中。

### 回答的诚实性约束

| 机制 | 做法 |
|---|---|
| 只依据资料 | 系统提示词明确要求"资料里没有的一律不写，不要凭常识补充命令、参数或数值" |
| 检索不到就不问模型 | 知识库里没有相关片段时直接说明并给出建议，**不调用模型** —— 让模型凭常识答运维问题，编出一条命令就可能造成故障 |
| 没有模型时退化 | 只给检索到的片段（界面标注"仅检索模式"），而不是报错或假装答不出来 |
| 模型失败时退化 | 保留检索结果并说明原因 |
| 引用可核对 | 回答里的 `[n]` 会标出"回答已引用"；模型引用了不存在的编号时**明确点出来**（这比不引用更危险），并提示"该部分没有依据" |
| 未标注引用时提示 | 提示"回答里没有标注引用编号，请自行核对" |
| 弱命中不挂到报告 | 巡检报告里的知识引用有最低相关度门槛（3.2）：只靠一个常见词偶然命中的（如"数据库错误"撞上"数据"二字）宁可不给，免得把人引到无关章节。**只看报告，不影响问答** —— 问答里弱命中的片段照样交给模型，模型会自己判断够不够 |

### 主题与语言

**顶栏最右侧**放着三样随时可能想改的设置：**模型**（点开模型设置面板，标签上显示当前模型名）、
**主题**（跟随系统 / 浅色 / 深色）、**语言**（中文 / English）。

它们放在顶栏而不是左侧栏，是因为左侧栏在窄屏（≤720px）下会变成抽屉滑出屏幕 —— 那时
"想切个语言"得先打开汉堡菜单才够得着。顶栏在所有视图、所有宽度下都在（实测 380px 宽时
三个控件仍在视口内且不溢出）。

主题与语言都存在浏览器的 localStorage 里 —— 这是"每台浏览器"的偏好，一个人用深色不该影响
同事；`config.toml` 的 `server.language` 只是"没有请求参数时的默认值"。模型配置则是服务端状态
（存在运行态文件里），换台电脑看到的是同一个当前模型。

### 主题

两套调色板定义在同一份语义变量上（`--bg` / `--panel` / `--text` / `--ok-text` / `--chip-warn-bg` …），
组件样式只写 `var(--xxx)`，不写具体颜色。这样"加一个主题"只是加一段变量，不必改组件；
反过来，样式里只要有硬编码颜色，那个地方在另一套主题下就会露馅（多半是看不见的黑字）。

首屏定主题的脚本放在 `<style>` 之前，否则浅色用户会先看到一帧深色。

### 语言

**用一个中文原文当键的词典**实现：代码里照旧写中文，翻译表是"中文 → 英文"的对照表。

| 为什么这么设计 | 说明 |
|---|---|
| 改动小 | 不必先把每句话改成 `inspect.title` 这类 key，也不会出现 key 与界面文案对不上 |
| 漏译不崩 | 查不到就返回中文原文，界面仍然是可用的，只是那句话没翻 |
| 谁都能校对 | 对照表就是双语清单，不需要开发参与 |

覆盖面由**测试**盯着，而不是靠人记得：

- `TestEnglishResponsesHaveNoChinese`：`?lang=en` 打一遍各接口（含报错路径），
  响应里出现中文即失败，并点名是哪个接口、哪段文案；
- `TestUIMessagesCoverAllLiterals`：扫页面里出现的每一句中文文案，词典里没有译文即失败。

这两条一起构成了这套 i18n 的账本：新加文案忘了配译文，或者翻译表被改坏，都会立刻红。

**语言如何贯穿**：

- 前端每个 API 请求带 `?lang=`，服务端按请求语言渲染（所以导出 PDF 也可以选语言：
  `/api/inspect/{id}/report.pdf?lang=en`）；
- **报告在生成时就定语言**：结论行里带计数与单位（"发现 130 条错误日志"、"可用 41.2%"），
  事后逐词替换翻不出正确语序；
- **结构化文案在阅读时也能切换**：检查项名称、状态标签、规则库的影响与处置建议都是词典条目，
  所以切到英文后重新查看旧记录，它们也跟着变（当时由模型生成的自由文本保持原样）；
- **模型提示词也跟着语言走**：让模型答中文却显示在英文界面里，是这套机制最容易漏的一环 ——
  知识库问答与日志分析各有一份英文提示词。回答的语言最终会跟着**提问的语言**走
  （用中文问就用中文答），这在混合团队里更符合直觉。

日志（journalctl）保持中文：它是给运维看的，混着翻反而不利于 grep。

## 界面有三个子页

| 子页 | 做什么 |
|---|---|
| **提问** | 输入问题 → 带引用的回答 |
| **导入文档** | 两种来源：**选择本地文件**（按钮，可多选，也可拖放）、**从服务器目录导入** |
| **文档与记录** | 已导入文档（**表格**：文档/来源文件/片段/大小/字数/导入时间/操作，点文档名直接在页面里打开阅读）+ **导入记录**（时间、来源、片段数、替换了谁、失败原因） |

把导入和提问分成两页，是因为导入是"偶尔做一次、要看清结果"的操作，提问是高频操作；
挤在一屏里会让提问框被导入表单推到下面。

### 随部署预置文档（装完就能用）

仓库根目录的 `knowledge/` 随包发布，`make deploy` 会把它装到
`/usr/share/backup-restore-agent/knowledge`，服务**启动时自动同步进知识库** ——
新部署不必先手工导入任何东西，提问和巡检引用立刻就有内容可用。

```
knowledge/
├── README.md            # 这个目录的说明（不会被导入）
├── zh/备份策略设计.md
├── zh/服务器巡检基线.md
├── zh/存储与磁盘故障处置.md
└── en/…                 # 同样三份英文版，检索按语言自然命中
```

**加自己的文档**：把 `.md` 放进 `knowledge/`（可以再建子目录），`make deploy`；
或者直接把文件放到服务器上的预置目录再 `systemctl restart backup-restore-agent`。

**同步规则刻意保守，不跟操作者抢控制权**：

| 情况 | 行为 |
|---|---|
| 知识库里没有同名文档 | 导入，标记为「预置」 |
| 有同名文档，且它也是预置的 | 内容不同就更新（升级时手册跟着刷新） |
| 有同名文档，是操作者自己导入的 | **不动它**（你的版本优先），启动日志记一条 |
| 你删掉过某个预置文档 | 记住名字，**以后不再补回来** |

界面上预置文档带一个「预置」标记。想让某份文档"归自己管"：重新导入一次同名文件即可，
之后同步就不再碰它（它变成你的版本）。关闭预置同步：`server.kb.seed_dir` 设为 `-`。

### 导入方式

**打开文档**：在「文档与记录」里点文档标题，右侧抽屉里直接渲染 Markdown（标题、列表、代码块、
表格、引用、链接）。渲染是**先整体 HTML 转义再套标签**手写的（不用现成 markdown 库：导入的文档来自外部，
转义顺序必须是这里能一眼看清的）——
用户上传的文档里塞 `<script>` 也只会显示成文字，实测无脚本执行、无 `javascript:` 链接。

> 原文是版本 3 起才开始保存的：更早导入的文档没有原文，打开时会提示"重新导入一次即可查看"，
> 而不是显示一片空白。检索与引用不受影响。

**本地文件**：`选择本地文件` 按钮（就是全站主按钮的样子）或把文件拖到虚线区域。选中的文件会先进"待导入清单"
（显示文件名、大小、是否超限），确认后再导入 —— 一次选十几个文件时，得先看清自己选了
什么、哪些超限。

**服务器目录**：把手册放到指定的导入目录里（默认 `/var/lib/backup-restore-agent/kb-inbox`，
用 `server.kb.import_dir` 改），界面上可以列出目录内容、逐个或批量导入，已导入的会标出来。

> ⚠️ 这个接口是"读服务器上的文件"，放开路径就等于给出**任意文件读取**（本服务没有鉴权，
> 任何能连到端口的人都能把 `/etc/shadow` 读进知识库再检索出来）。所以做了三层限制：
> 只能读指定目录内的文件、只认 `.md/.markdown/.txt`、路径解析后（含软链接）必须在目录内。
> 目录不存在时当作空目录，不报错。

**粘贴**：直接贴 Markdown 文本，可选填文件名。

支持 `.md` / `.markdown` / `.txt`。同名文档**替换**而不是并存（改完重新导入是最常见的动作，
留着旧版本会检索到过时内容），旧版本的去向在导入记录里。

### 导入记录

每次导入都留一条记录：时间、文件名、来源（本机上传／粘贴／服务器目录）、片段数、字节数，
以及**替换了哪一份旧文档**；失败也留记录并写明原因（例如"文档内容为空"、"超过单份上限"）。
记录落盘、重启后还在，最多保留 200 条（`server.kb.max_records`），可一键清空（不影响文档）。

默认限制：单份 2 MB、总量 16 MB、文档数 200；片段约 400 字、重叠 80 字。
切分按 Markdown 标题层级（`#`/`##`/…），所以引用能落到"哪一节"；代码块内部的 `#` 不当标题。

两个从实际使用中补上的细节：

- **片段正文带上完整章节路径**。小节标题常常不含文档关键词（文档叫《换盘流程》、小节叫《步骤》），
  只按小节文本索引的话，问"换盘流程是什么"召回不到那一段。带上路径后同一文档的片段都能被文档关键词召回，
  引用也一眼看得出"这段出自哪一节"。
- **过短的片段并入下一段**。一份几十字的小手册切成"# 换盘流程"和"## 步骤 + 两步操作"两段时，
  问"换盘流程是什么"会命中只有标题的那一段 —— 关键词在那儿，内容却为空，模型只能答"资料里没有"。
  合并之后标题与正文同段，召回的就有实质内容了。

> 知识库落盘在 `/var/lib/backup-restore-agent/kb.json`（0600）。里面是文档切出来的片段，
> 不含任何凭据。切分规则变了以后老文档不会自动重算（落盘里没有原文），启动时若发现落盘
> 版本较旧会提示重新导入 —— 这不是数据损坏，只是章节路径可能按旧规则。

## 运行时清单（应用与目标介质）

"能备份哪些应用"与"能备份到哪些介质服务器"**来自运行时接口**，不是写死在代码里的 ——
新上线的库、新扩容的存储池不需要改代码或重启服务。

```toml
[server.catalog]
url = "https://backup-platform.intra/api/inventory"
api_key_env = "BRA_CATALOG_KEY"
ttl_seconds = 60
```

接口约定（字段名容错，见下）：

```json
{
  "applications": [
    {"kind": "oracle", "display": "Oracle 19c", "source_type": "database",
     "aliases": ["orcl", "甲骨文"], "note": "生产库",
     "options": [
       {"field": "auth_mode", "label": "认证方式", "kind": "enum",
        "choices": ["系统认证", "账号密码"],
        "choices_map": {"系统认证": "os_auth", "账号密码": "password"}},
       {"field": "channels", "kind": "int", "min": 1, "max": 32,
        "suggest": ["2", "4", "8"]}
     ]},
    {"kind": "dameng", "display": "达梦 DM8"}
  ],
  "media_servers": [
    {"id": "pool-a", "name": "本地磁盘池A", "type": "local", "path": "/u01/backup"},
    {"id": "tape-01", "name": "磁带库01", "type": "tape"},
    {"id": "dr-s3", "name": "异地对象存储", "type": "s3", "bucket": "dr-backup",
     "region": "cn-north-4"}
  ]
}
```

清单如何影响行为：

| 位置 | 影响 |
|---|---|
| 提示词 | 把清单里的应用与介质**原样列出**，模型只从中选择，不会编出环境里没有的东西 |
| 应用识别 | `kind` 不在清单里 → 给警告（可能抽错了对象，也可能清单没覆盖） |
| 参数追问 | 接口为某应用声明了 `options` → **以接口为准**追问与校验；没声明 → 沿用内置驱动的参数定义 |
| 目的地候选 | 候选值就是清单里的介质服务器（显示为"服务器名 + 落点"），点选后落点取自该服务器定义，并记进计划的 `media_server` |
| 界面 | 头部徽章与"模型设置"面板显示清单来源、数量，可一键刷新 |

**容错**：不要求对方改接口。外层包装认 `{ok, data}` / `{data}` / `{result}`；列表字段认
`applications`/`apps`/`sources`/`engines` 与 `media_servers`/`targets`/`storage`/`destinations`；
字段名认 `kind`/`type`/`id`/`code`、`display`/`name`/`label`、`path`/`dir`/`mount_point` 等常见写法。
应用与介质也可以分在两个地址（`applications_url` / `media_servers_url`）。

**降级**：接口不可用时退回内置清单并在界面上说明原因；**曾经成功过则沿用上次结果** ——
环境没变，只是接口抖了一下。整条链路不因清单接口故障而不可用。

## 界面

对话式布局，左侧是历史对话：

- **左侧栏**：历史会话按"今天 / 最近 7 天 / 更早"分组，每项显示意图（备份/恢复）与状态
  （已完成 / 待补充 N 项）。点开可续接，× 可删除。**历史会落盘**，重启服务后仍在。
- **中间**：对话流。每一轮以卡片展示已识别字段、待补充问题、提示与风险、处理过程；
  计划完成后在对话末尾直接给出 JSON，带复制与下载。
- **每个追问都给推荐选择 + 自定义输入**：
  - 推荐值分两类：`choices`（封闭候选，如目的地类型、认证方式）与
    `suggestions`（常用值，如"凌晨1点""保留30天"）。**点一下直接提交**。
  - 两类推荐值都来自后端槽位表，前端不硬编码 —— 新增引擎时自动跟上。
  - 没有合适推荐值的参数（如目标主机）只给输入框，不会硬凑。
  - 也可以在底部输入框说一句话（如"都是凌晨1点，保留14天，存本地 /u01/backup"）→
    作为追加需求交给抽取流程理解，一次补齐多个字段

  两条路并存是有意的：只留前者会退化成逐格填空，只留后者会丢掉确定性回填的可靠。
  已完成的对话继续输入即是在此基础上修改（"保留期改成30天"）。
- 窄屏下左侧栏收起为抽屉。

## 模型配置

两种方式，按场景选：

### 方式一：在网页上直接配（推荐，无需 ssh）

打开页面右上角 **模型设置**：选择厂商 → 填 API Key → 保存并启用。三个动作即可，
不用改任何文件。保存后会立刻成为当前模型，并**跨重启保留**。

- 厂商下拉内置 12 个预设（DeepSeek / 千问 / Kimi / 智谱 / 豆包 / OpenAI / Azure /
  OpenRouter / 硅基流动 / Ollama / vLLM / LM Studio），选中后自动带出接口地址与默认模型
- 也可以选"自定义"，填任意 OpenAI 兼容端点的 `base_url` 与模型名
- 本地厂商（Ollama 等）不需要 Key，直接保存即可用
- 保存后可点 **连通性+冒烟** 一次验证两件事：Key/端点/模型名是否正确，以及模型的
  中文抽取能力是否够用

**密钥存在哪里**：`/var/lib/backup-restore-agent/runtime.json`，权限 `0600`，只属于服务用户。
它**不会写进 `config.toml`**，也不会回显到界面或日志。之所以单独一个文件：

- `config.toml` 是 `0640 root:bra`，服务用户本来就无法写它；为让服务能写而放松权限是安全倒退
- `config.toml` 应保持"管理员声明的基线"，升级时会被保留，不适合被网页反复改写
- 分开之后，网页创建的配置可以标注来源、单独删除，与基线互不污染

同名时网页配置覆盖配置文件；删掉网页配置后，配置文件里的同名定义重新生效。
省略配置名时会自动避让（如同名则生成 `deepseek-2`），不会静默覆盖管理员的声明。

想关掉这个能力：在 `config.toml` 里设 `"allow_ui_config": false`，此后模型配置只能
通过配置文件维护（界面上的表单会隐藏，保存接口返回 409）。

> 注意：当前版本**没有鉴权**（见下文"不在当前范围"）。开放网页改配置意味着能访问该
> 端口的人就能改动模型配置。请只在受控内网暴露该端口，或设 `allow_ui_config: false`。

### 方式二：写 config.toml（适合批量/受控部署）

配置文件查找顺序：`-config` 参数 → `BRA_CONFIG` → `./config.toml`
→ `/etc/backup-restore-agent/config.toml`。完整示例见 [config.example.toml](config.example.toml)。

```toml
[server]
host = "0.0.0.0"
port = 8081
max_turns = 10

[llm]
default_profile = "deepseek"

[llm.profiles.deepseek]
preset = "deepseek"
api_key_env = "BRA_DEEPSEEK_KEY"

[llm.profiles.local]
preset = "ollama"
model = "qwen2.5:14b"
```

> 配置是 **TOML**（旧版的 `config.json` 不再读取）。升级时 `install.sh` 会把旧文件改名留档，
> 并沿用原来的端口 —— 其余自定义项需要手工搬过来。
> **未知的键会导致启动失败**，这是有意的：拼错的键被静默忽略时，症状是"配置看着生效其实没生效"。

填 `preset` 即自动带出 `base_url` 与默认模型，避免手抄 URL 出错。内置预设：

| preset | 说明 |
|---|---|
| `deepseek` | DeepSeek（默认，中文好、便宜） |
| `qwen` / `kimi` / `glm` / `doubao` / `siliconflow` | 通义千问 / Kimi / 智谱 / 豆包 / 硅基流动 |
| `openai` / `openrouter` / `azure_openai` | OpenAI / OpenRouter / Azure（填部署名） |
| `ollama` / `vllm` / `lmstudio` | 本地与内网模型，数据不出网 |

任何 OpenAI 兼容的 `/chat/completions` 端点都能直接用：`provider` 留
`openai_compat`，自己填 `base_url` 与 `model` 即可。

### 密钥处理

- 配置文件里的密钥只接受三种来源：`api_key_env`（环境变量）> `api_key_file`（**要求 0600**）
  > `api_key`（仅允许本地端点）
- 明文 `api_key` 配给远程端点会在启动时报错，避免密钥随配置文件扩散
- 网页上粘贴的密钥**不受上述限制**，落在 `0600` 的运行态文件里。这是刻意的不对称：
  那个文件由服务自己写、从不经人手编辑或提交，不存在扩散路径；若也一刀切禁止，
  用户就无法在界面上直接粘贴密钥，而那正是这个功能的意义
- 密钥不出现在日志、接口响应或网页里；接口只报告 `has_key` 布尔值
- 网页上的"测试连通性 / 抽取冒烟"能立刻区分**Key 错**、**模型名错**、**连不上**与
  **模型中文抽取能力不足**——现象都是"解析失败"，处置方式却完全不同

### 结构化输出的降级链

不同端点的能力不一致，客户端自动逐级降级：

```
response_format={"type":"json_object"}
  └─ 400 不支持 ─> 记入能力缓存(后续不再试) + 去掉该参数重试
       └─ 仍拿不到 ─> 剥代码块围栏 / 截首尾花括号抢救 JSON
            └─ 连续 3 次失败 ─> 422 + 明确的换模型建议
```

### 模型能力门槛

复合 schema 与中文术语映射有一定难度。本地模型建议 **14B 以上**；7B 以下抽取质量会
明显下降，那种情况建议直接用 demo 模式演示。

## 新增一个引擎

以"支持 SQL Server"为例，只需新建 `internal/driver/sqlserver.go`：

```go
func init() {
    Register(&Driver{
```

要点：

- 用 `Optional: true` 标记有安全默认值的槽位（缺失只出提示，不阻塞）
- 用 `SatisfiedWhen` 表达条件必填（如 PostgreSQL 选物理备份时不需要库名）
- `Desc` 会原样进提示词，把"中文标签 -> 代码值"的对应关系写在里面最有效

## 部署需要什么

**一句话**：一台装了 systemd 的 Linux（x86_64）+ root 权限装一次 + 一个空闲的 80xx 端口。
没有中间件、没有运行时、没有数据库，二进制是静态链接的（`CGO_ENABLED=0`，不挑 libc 版本）。

### 目标服务器

| 项 | 要求 |
|---|---|
| 操作系统 | Linux + **systemd**（硬要求：安装要装 unit；在 Debian 13 上验证） |
| 架构 | x86_64（`make` 里 `GOOS/GOARCH` 可改，交叉编译不需要目标机有 Go） |
| 安装权限 | root（建服务用户、写 `/opt` 与 `/etc`、装 systemd unit） |
| **运行权限** | 专用无特权用户 `bra`（服务只读信息、不改目标机，不需要任何特权） |
| 资源 | 单进程；常驻内存几十 MB（知识库索引在内存里），二进制约 12 MB |
| 端口 | 一个 80xx（部署时从 8081 起自动挑空闲端口） |

### 需要哪些软件

| 类别 | 说明 |
|---|---|
| **必需** | `systemd`（安装脚本启动前会检查） |
| **巡检功能必需** | OpenSSH **客户端**：`ssh` 与 `ssh-keygen`。巡检调用系统 ssh 而不是 Go 的 SSH 库（与运维手工排障同一客户端、TOFU 语义一致），`ssh-keygen` 用来计算主机指纹 |
| 可选 | `ss` 或 `netstat`（部署时端口预检，缺了只是警告）、`curl`（部署后自检 `make smoke`） |
| **都不需要** | Python / Java / Node / Go 工具链 / 数据库 / Nginx 反向代理 / **中文字体** / PDF 工具 —— 内置 HTTP 服务、PDF 生成与两份可嵌入字体 |

> 被巡检的目标机**不需要装任何东西**，只要跑着 sshd。客户端只要一个现代浏览器。

### 网络

| 方向 | 用途 | 是否必需 |
|---|---|---|
| 入站 `0.0.0.0:<80xx>` | 浏览器访问界面与接口 | 必需 |
| 出站 → 模型端点 | 如 `https://api.deepseek.com`，或内网 Ollama/vLLM | 用真实模型时必需；**demo 模式完全离线可用** |
| 出站 → 被巡检主机 `22/tcp` | 巡检通过 SSH 采集 | 用巡检功能时必需 |
| 出站 → 清单接口 | 动态查询"能备份哪些应用、能备份到哪些介质" | 可选，不配则用内置清单 |

### 部署时要填的东西

| 项 | 填在哪 | 说明 |
|---|---|---|
| 模型 | 界面「模型」→ 选厂商 + 填 API Key | 不填就是 demo 模式（关键词规则），功能可演示但抽取能力有限 |
| 巡检凭据 | 每次巡检时在界面填 IP / 用户 / 密码或私钥 | **不落盘**，只在本次连接的内存里存活 |
| 知识库文档 | 放进 `knowledge/` 随包发布，或界面导入 | 预置文档已随包提供三份中英手册 |

### 手工部署（不用 `make deploy`）

`install.sh` 做的事都可以手做：把二进制放到任意路径、写一份 `config.toml`、写一个
systemd unit（`User=` 指向一个无特权用户、`StateDirectory=` 指向数据目录）即可。
用安装脚本的好处是端口预检、目录权限、加固项与部署后自检都已经验证过。

## 部署

目标机由 `REMOTE` 指定（默认是占位值，部署时传真实主机）：

```bash
make deploy REMOTE=root@your-server        # 只本次生效
# 或改 Makefile 里的 REMOTE, 或写进你自己的 shell 配置
```

```bash
make package   # 编译 + 测试 + 打包
make deploy    # 推送到目标机并安装
make status    # 查看状态与健康检查
make smoke     # 在目标机跑部署自检
make logs      # 跟踪日志
```

**端口不硬编码**：`deploy/install.sh` 在部署时用 `ss -lnt` 实测，从 8081 起在
8081–8099 内挑选第一个空闲端口。若整段被占用则明确报错并列出占用者——绝不静默换到
80xx 之外，那样会让按约定配好的防火墙规则失效。升级时若原端口仍空闲则沿用，避免端口漂移。

安装布局：

| 项 | 路径 |
|---|---|
| 程序 | `/opt/backup-restore-agent/bin/backup-restore-agent` |
| 配置 | `/etc/backup-restore-agent/config.toml`（0640） |
| 密钥 | `/etc/backup-restore-agent/env`（0600，systemd `EnvironmentFile`） |
| 网页配置 | `/var/lib/backup-restore-agent/runtime.json`（0600，systemd `StateDirectory`） |
| 对话历史 | `/var/lib/backup-restore-agent/sessions.json`（0600，超出 30 条自动裁剪最旧的） |
| 巡检记录 | `/var/lib/backup-restore-agent/inspections.json`（0600，不含凭据） |
| 主机指纹 | `/var/lib/backup-restore-agent/known_hosts`（服务用户无家目录，默认落这里才可写） |
| 知识库 | `/var/lib/backup-restore-agent/kb.json`（0600，片段 + 原文 + 导入记录） |
| 待导入手册 | `/var/lib/backup-restore-agent/kb-inbox`（把 .md 放这里，界面上可一键导入） |
| 预置手册 | `/usr/share/backup-restore-agent/knowledge`（随包安装，启动时同步进知识库） |
| 服务 | systemd `backup-restore-agent.service` |

服务以专用无特权用户 `bra` 运行（本服务只做解析与 JSON 生成，不需要任何特权），
并启用了 `NoNewPrivileges`、`ProtectSystem=strict`、`PrivateTmp` 等加固项。

部署后自检 `deploy/smoke.sh` 为**纯 bash + curl**，不依赖 jq 或 python——单二进制的
部署优势不该被运维脚本抵消。它覆盖健康检查、内置页面、驱动列表、密钥不泄露、
"追问→补齐→ready"完整闭环、巡检凭据路径、知识库导入检索、主题与语言、错误码等，
目前 135 项断言（`make smoke` 会打印通过数）。

## 测试

```bash
make test            # 全部用例 (561 个顶层测试函数)
make check           # 格式化 + vet + 测试
make ci              # 完整门禁: 静态构建 + 格式 + vet + 竞态 + 密钥扫描 + TLS 校验 + staticcheck + govulncheck
```

`make ci` 里两条会失败的检查值得单独说明（它们不是提醒，是门禁）：

- **`secret-scan`**：扫描仓库里是否出现明文密钥、私钥块或非空的凭据示例。测试里若确实需要
  "长得像密钥的假样本"，必须在同一文件里写明 `secret-scan:allow-test-key` —— 强制人工判断一次。
- **`verify-tls`**：不允许出现 `InsecureSkipVerify`；出现 `tls.Config` 的文件必须显式声明
  `MinVersion`（不能依赖 Go 的缺省值），且不得低于 TLS 1.2。

构建需要 **Go 1.26.8+**（`go.mod` 里用 `toolchain` 钉住）。这是安全要求而不是偏好：Go 只为最近
两个大版本提供安全补丁，钉在旧补丁版时 `govulncheck` 会报出几十个已修复的标准库漏洞。
首次构建会自动下载该工具链（约 100 MB，之后缓存在 `GOMODCACHE`）。

`staticcheck` 与 `govulncheck` 是开发期工具，用 `make install-tools` 安装；缺失时门禁**报错而不是跳过**。

重点用例：

- `internal/schema`：**防漂移测试**——用反射比对结构体字段与生成的 JSON Schema，
  漏写字段会直接失败（Go 没有 Pydantic 的自动 schema 能力，这是那道防线）
- `internal/driver`：别名边界（`pg` 不误伤 `gpg`/`page`）、中文标签回填、条件必填、越界校验
- `internal/llm`：用 `httptest` 验证**降级链**、`json_object` 能力缓存、HTTP 状态到错误类型的分类
- `internal/agent/acceptance_test.go`：**验收用例**——直接编码需求方给的原句，
  断言抽取准确、追问恰好 4 项且不重复、补齐后 `ready`、无法识别的回答靠轮次上限熔断
- `internal/agent/session_test.go`：会话跨重启保留、0600 权限、历史损坏不影响启动、
  标题按字符截断（不切坏中文）、自由文本补充累积、历史裁剪上限
- `internal/catalog`：**清单来自接口**——容错解析（外层包装与字段别名）、TTL 缓存、
  接口抖动时沿用上次结果、从未成功才退回内置清单、鉴权头（默认 Bearer 且可自定义）、
  应用与介质分接口查询、空清单与非法响应不静默通过
- **清单驱动行为**（`internal/agent/catalog_test.go`）：目的地候选项来自接口、
  选中介质服务器后落点取自其定义、同类型落点替换而不同类型追加、
  接口声明的应用与参数能被追问与校验、提示词里带上清单、接口挂掉不影响流程
- `internal/kb`：**知识库与检索**——中文二元组分词（无分词器）、按标题层级切分（代码块不切、
  超长片段带重叠、段落/句子边界优先）、BM25 排序（标题加权、长片段归一）、
  **检索质量用真实感手册与真实提问检验**（"zpool 校验失败怎么办"必须命中 ZFS 手册那一节）、
  相关度阈值两侧都钉住（真命中不能被误伤、偶然命中必须挡住）、落盘往返与坏文件容忍
- `internal/kb/ask_test.go`：**回答的诚实性**——只依据资料、检索不到不调用模型、
  没有模型时只给片段、引用不存在的编号要点出来、未标注引用要提示、
  扩展词只补充召回不能改变排序
- `internal/i18n`：**中英文文案**——用中文原文当键 (代码里照旧写中文, 漏译退化成原文),
  词典分文件便于校对；英文响应不泄中文、界面文案全覆盖都由测试盯着
- `internal/inspect`：**巡检的解析与判定**——负载/内存/df/温度/日志的解析与阈值、
  **"读不到温度/日志"必须报无法判定**（不能显示成正常）、通配伪文件系统过滤、
  日志去重（按时间戳与 pid 归一）、结论行随报告返回
- `internal/inspect/ssh_password_test.go`：**凭据传递链路**——用假 ssh 逐参数记录，
  断言密码只走环境变量（不进 argv）、`SSH_ASKPASS` 指向本程序、私钥为 0600 临时文件且用完删除、
  主机指纹策略确实传给了 ssh、ssh 错误按原因分类、**认证方式按凭据裁剪**、
  `SSH_ASKPASS_REQUIRE` 以环境变量而非配置项下发（写成 `-o` 会让 ssh 直接拒绝启动）
- `internal/pdfdoc`：**PDF 生成**——字体解析（cmap 取字形、hmtx 取字宽）、子集化的表重组与
  校验和、缺字形的替代与统计、ToUnicode 映射（决定复制出来是不是中文）、中英混排断行与行首禁则、
  **一行几万字符的文本也要线性时间折行**（曾经是平方复杂度，一次导出能挂住请求）
- `internal/inspect/pdf_test.go`：**报告内容与版面**——结论/元信息/证据都在、失败报告说明未采集、
  长证据跨页续画不浪费页面、固定文案里每个字都有字形
- `internal/web/server_test.go`：**内联脚本体检**——页面调用的函数必须都已定义，
  且脚本语法上必须成立（字符串/正则/注释闭合、闭合的字符串后不能紧跟标识符字符）。
  这条来自一次真实事故：新增文案里一个没转义的直引号让**整段脚本一行都没执行**，
  三个标签全部点不动，而当时所有 Go 测试都是绿的（它们断言的是"页面里有这个字符串"）
- `internal/inspect/ssh_process_test.go`：**两条"不报错但会悄悄烂掉"的故障**——
  askpass 助手认不出自己（缺标记时会**再起一个服务实例常驻**，一次连接泄漏一个进程，
  且 ssh 永远等不到密码而挂死）、卡死的 ssh 能否被总预算连同派生进程一起收掉
- **推荐值必须可用**：遍历所有驱动的全部推荐值，逐个跑槽位解析器，解析不了就失败 ——
  点一下即提交的设计下，一个解析不了的推荐值比没有推荐更糟
- `internal/config`：密钥来源优先级、明文密钥拒绝远程端点、密钥文件 0600 强制、
  **运行态文件 0600 与原子落盘**、留空保留原密钥、配置名与 preset 校验、
  **预设必须显式声明是否需要密钥**（靠 bool 零值会让云端配置静默变成"无需密钥"）
- `internal/web`：HTTP 完整闭环、错误码、profile 切换、**保存后响应仍不泄露密钥**、
  同名覆盖与自动避让、配置文件项拒绝删除、`allow_ui_config=false` 时返回 409

## 不在当前范围

按 MVP 边界刻意不做：脚本渲染与执行（不生成 RMAN/xtrabackup 命令、不连数据库）、
凭据解析（只存 `credential_ref` 引用）、鉴权、HTTPS、多实例部署、恢复演练执行、巡检的阈值可视化配置（当前写在代码里）。

（会话历史、模型配置与所选模型都已落盘持久化；单机部署下这些文件都在
`/var/lib/backup-restore-agent/`。应用与目标介质清单来自运行时接口，已不是静态列表。）

其中**鉴权**与网页改配置相关：能访问该端口的人就能新增/修改模型配置。当前仅适合
受控内网部署；暴露到更大范围前，请先加鉴权或设 `allow_ui_config: false`。

计划 JSON 的字段已为后续渲染器留好结构位——加渲染器是纯函数增量，不需要改 schema。
