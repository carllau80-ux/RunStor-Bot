# 服务器巡检基线

## 巡检在看什么

| 检查项 | 判据 | 常见误报 |
| --- | --- | --- |
| CPU 负载 | 每核 1 分钟负载 >1 告警 / >2 严重 | 备份窗口内的短时高负载属正常 |
| 内存 | 可用 <20% 告警 / <10% 严重；swap 使用 >50% 关注 | Linux 用空闲内存做缓存，看 **可用** 而不是空闲 |
| 磁盘分区 | 使用率 ≥80% 告警 / ≥90% 严重 | tmpfs/overlay 等虚拟文件系统不计入 |
| 温度 | ≥80°C 告警 / ≥90°C 严重 | **虚拟机读不到传感器是正常的**，会标为"无法判定" |
| 严重错误日志 | 内核 panic/OOM/硬件错误、I/O 错误等 | dmesg 是"本次启动以来"，可能包含很久以前的记录 |
| 服务状态 | 有 failed 的 systemd 单元 | 一次性任务（oneshot）失败不一定影响业务 |

**"无法判定"不是"正常"**：读不到温度、读不到日志，报告会明确说读不到，不要当成健康。

## 报告怎么读

1. 先看结论条：严重 / 告警 / 正常 / 无法判定；
2. 再看"影响与处置建议"：每条问题给出影响与分步处置，按顺序做；
3. 证据块是原始输出，判断结论是否可信时对着看；
4. 报告里带"规则库"标签的结论来自内置故障特征库；带"模型分析"标签的来自大模型，需结合现场判断。

## 分级处置

- **严重**（数据可能受损或服务已中断）：立即处理，先确认备份可用，再动手；
- **告警**（趋势不好但还能跑）：当周内处理，先记录下来；
- **无法判定**：补上采集手段（装传感器、放开日志权限）后重跑一次。

## 日志时间窗

巡检日志来自三个来源，时间范围不同，读的时候要分清：

- `journalctl -p err`：近 24 小时；
- `dmesg`：**本次启动以来**的环形缓冲，可能是几周前的事；
- `/var/log` 尾部：文件里最后若干行。

所以"发现 N 条错误日志"不等于"最近发生的"。要判断新旧，看行首的时间戳
（journald 是绝对时间，dmesg 是开机以来的秒数）。
