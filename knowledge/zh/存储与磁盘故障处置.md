# 存储与磁盘故障处置

## ZFS 校验失败（checksum mismatch）

**含义**：从盘上读出的数据与校验和不符。ZFS 会用冗余副本自动修复能修的；
修不好说明同一块数据的所有副本都坏了 —— 属**静默数据损坏**，比磁盘直接坏更危险。

处置顺序：

1. `zpool status -v` 记下受影响文件清单（写进工单）；
2. 确认最近备份**不在同一个池上**，并实际验证可读；
3. `zpool scrub <pool>` 让 ZFS 修复可修复的块；
4. 检查硬件：内存（`memtest86+`）、数据线、HBA/背板、电源——这类错误常源于链路；
5. 若 vdev 错误数持续增长，尽快换盘。

## 存储池降级（DEGRADED / FAULTED）

DEGRADED 还能读写，但**再坏一块盘就可能整池不可用**；FAULTED 则数据集已经读写失败。

1. `zpool status` 确认缺哪块盘、能否 resilver；
2. 换盘后 `zpool replace`，等待 resilver 完成，期间避免大批量写入；
3. 同一槽位反复掉盘通常不是盘的问题，而是背板/线缆/电源。

## 磁盘 I/O 错误

`blk_update_request: I/O error`、`medium error` 这类是设备层报错。

1. `smartctl -a /dev/sdX` 看重映射扇区、待定扇区、CRC 错误计数；
2. CRC 类错误多为链路问题（线缆/背板/电源），不一定是盘；
3. 文件系统若已转为只读挂载（`Remounting filesystem read-only`），先停业务再考虑 fsck；
4. 确认数据可读、备份可用，准备替换盘。

## iSCSI 链路：登录被拒

日志出现 `iSCSI Login negotiation failed`、`Security negotiation failed` 或
`is not authorized to access iSCSI target portal group` 时，是目标端拒绝了发起端。

1. target 侧核对 ACL：发起端 IQN（`cat /etc/iscsi/initiatorname.iscsi`）是否在白名单；
2. 核对 CHAP：`/etc/iscsi/iscsid.conf` 的用户名/密码与存储侧是否一致，是否要双向认证；
3. 确认 3260 可达、防火墙放行；
4. 改完配置 `systemctl restart iscsid open-iscsi`，再 `iscsiadm -m session -R`。

> `MODE SENSE: unimplemented page` 是内核探测设备能力时得到的"不支持"回应，
> **本身不代表读写失败**（iSCSI 目标、磁带机、虚拟设备常见）。
> 只有同一设备同时出现 I/O 错误或性能下降时才需要处理。

## 空间不足

1. `df -h` 定位分区，`du -xh --max-depth=1 / | sort -h` 找占用大户；
2. 优先清理日志与临时文件，确认 logrotate 生效；
3. `lsof +L1` 查"已删除但仍被进程占用"的文件；
4. 长期方案是扩容或迁移，并给该分区加容量告警。

> 根分区写满会连带影响登录与临时文件创建，症状看起来像"系统坏了"——先 `df -h` 排除它。
